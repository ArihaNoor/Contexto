The problem

An answer you can't check is worse than no answer.

Anyone working through a long contract, paper, or specification loses hours to the same task: finding the one paragraph that settles a question. Pasting the document into a general-purpose chatbot fails twice over.

First, the model fills gaps with plausible invention — ask about a clause that isn't there and you get a confident answer anyway. Second, there is nothing to verify against: no page, no quoted passage, no trail. Where being wrong carries a cost, that is a liability dressed as an answer.

How it works

PDF in, cited answer out.

Nothing exotic — the RAG pipeline itself is well-trodden ground. What matters is where each stage runs, and what it refuses to do.

01 Ingest PyPDF extracts text with page metadata. A recursive character splitter produces overlapping ~1000-character chunks that respect paragraph and sentence boundaries instead of cutting mid-thought.
02 Embed Each chunk becomes a 384-dimension vector via BAAI/bge-small-en-v1.5, running on CPU through fastembed's ONNX runtime. No GPU, no torch, no per-token cost, no network hop. A 20-page PDF never leaves the machine.
03 Index Vectors land in a ChromaDB collection named for that upload's session id — one collection per document, never a shared one.
04 Retrieve The question is embedded and matched by cosine similarity. The TOP_K=4 closest chunks become the grounding context — and, simultaneously, the citations.
05 Generate Context, chat history, and the guardrail prompt go to the language model, which streams its answer back over server-sent events — sources first, then tokens.

Engineering

Five decisions that cost me something to learn.

Every one of these started as a failure I actually hit — a dead vendor, a lying benchmark, a leak waiting to happen. This is the part of the build that isn't in any tutorial.

01 — Isolationapp/services/vectorstore.py
app/api/routes.py

Isolation enforced by structure, not by a filter

Risk

The conventional design is one shared vector collection with a session_id metadata filter on every query. It works — until the filter is omitted in one code path, and one user's document surfaces inside another user's answer.

Decision

Each upload gets its own ChromaDB collection. Cross-document leakage stops being something to remember and becomes structurally impossible — a query is scoped to a collection that only ever held one document. Cleanup simplifies too: DELETE /clear is a single delete_collection call instead of a filtered mass-delete.

02 — Portabilityapp/services/llm.py
app/config.py

A vendor-agnostic LLM layer, forced by a real outage

Broke

The first build bound directly to the huggingface_hub SDK. The configured model turned out not to be served by any inference provider enabled on the account — every query returned a 502. Then, mid-benchmark, the account's monthly credits ran out and the service went down entirely.

Decision

Both failures had one root cause: a hard dependency on a single vendor's SDK and a single vendor's quota. A portfolio project that only works while a free tier holds out isn't finished. Since every provider worth using speaks the OpenAI /chat/completions protocol, I replaced the SDK binding with a small httpx client that speaks that protocol directly, plus named presets per provider.

# From a dead hosted provider to a free local model:
LLM_PROVIDER=ollama
LLM_MODEL=llama3.2
Result

Two lines. No code change. The service runs fully offline at zero marginal cost, and moving to OpenAI or Gemini for production is the same two-line edit. The whole abstraction is one module that nothing else imports.

03 — Latencyapp/api/routes.py — /query/stream
static/app.js

Streaming, because the bottleneck wasn't where the spec assumed

Missed

The spec set a 3-second target for query responses. Measured against a hosted provider, full answers averaged 6.2s — roughly double.

Decision

Rather than guess, I instrumented the two halves separately. Retrieval — embedding the question and running the vector search — finishes in milliseconds. Essentially all the latency was the model writing prose, and no amount of retrieval tuning was going to touch it. So I changed what the user waits for instead: the service streams over SSE, and because retrieval completes long before generation does, citations are sent as the very first event. The sources are on screen and readable before the model has written a word.

04 — Measurementscripts/benchmark.py
spawns a real uvicorn process

A benchmark that was lying to me

Broke

My first streaming benchmark reported that all 286 tokens arrived in the same instant — a 0.00s spread, which would have meant the streaming implementation did precisely nothing.

Decision

Before changing any code, I tested the layers separately. The provider client streamed correctly in isolation. The culprit was FastAPI's TestClient, which buffers text/event-stream responses entirely before returning them. Against a real uvicorn process, streaming behaved exactly as designed. The fix was to the instrument, not the product — the harness now starts a real server, because a number produced by the wrong instrument is worse than no number.

05 — Failure modesapp/services/llm.py
covered by tests/test_units.py

Errors that tell you what to do next

Broke

Early on, provider failures were caught broadly and returned as f"LLM generation failed: {exc}" — leaking internals to the user while telling them nothing actionable.

Decision

Each failure mode now maps to a specific instruction. A 402 says the account is out of credits and suggests switching to a local provider. A connection refused against localhost asks whether ollama serve is running. An unsupported model names the environment variable to change. Anything genuinely unexpected is logged with a full traceback server-side and returned as a generic 500 that leaks nothing — a behaviour that is itself covered by a test.

Where it stops

Knowing where a system ends is part of engineering it.

These are documented in the README rather than hidden, along with what I'd build to close each one.

Chat memory is in-process History lives in a dict — lost on restart, not shared across workers. Vector data persists; history doesn't. Next: Redis-backed history.
Text-based PDFs only Scanned documents return “no extractable text”. Next: a Tesseract OCR fallback would widen coverage considerably.
Dense retrieval only Vector search alone underperforms on keyword-heavy queries — clause numbers, part codes, defined terms. Next: BM25 hybrid plus a reranking pass.
No authentication Session ids are unguessable 128-bit values — adequate for single-user use, not for multi-tenant deployment. Next: real auth before any shared deployment.
